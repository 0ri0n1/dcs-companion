# Single-player mission awareness

This feature is enabled by default following the user's explicit request. It shows live opposing mission units as a separate **Mission awareness** layer. It is not an aircraft radar, RWR, sensor detection, or stored mission overlay. The scope's **Mission enemies** toggle controls visibility. For direct backend launches, `DCS_DASH_MISSION_AWARENESS` can disable collection when set to a value other than `YES`; the normal launcher sanitizes inherited settings and uses the installation default.

The backend sends three fixed read-only requests to the already installed loopback Fiddle bridge: hooks metadata on 12081, mission units on 12080, then hooks metadata on 12081 again. Credentials are read privately from the existing hook configuration, remain in memory, and never enter API responses or logs. Browser requests cannot supply Lua, addresses, file paths, coalition selectors, or unit selectors. No DCS installation, Saved Games, hook, exporter, mission, or collector file is edited. No new UDP listener is opened.

Before requesting any enemy units, the hooks must explicitly report `DCS.isMultiplayer() == false`, `DCS.getPause() == false`, a current mission name, aircraft type, and finite model time. Missing or ambiguous values stop the request. After the mission response, the same checks must still agree. Any failure clears the contacts. `DCS.isServer()` is not used because it is also true in multiplayer servers.

**The two mode checks span separate requests and are not atomic.** A transition can occur after the preflight check and before the queued mission read executes. The postflight gate discards that result if the mode or mission changed. The app never initiates the unit request when preflight reports multiplayer, paused, or unknown, and never publishes a result whose postflight check disagrees. It does not claim that enumeration is impossible during that narrow transition window.

The preferred single-hook cross-environment return route was tested with harmless fixed scalars on this installation. `net.dostring_in("mission", "return constant")` worked, but `a_do_script("return constant")` returned nil both paused and advancing. A direct scripting-state return and a mission-to-GUI mode return were unavailable. The app therefore uses the existing working mission HTTP bridge and does not change API permissions, install a hook, or add runtime globals to work around this limitation. The installed `API/Sim_ControlAPI.md` documents direct return values at lines 322–325, but this runtime did not exhibit that behavior.

`AwarenessReader.snapshot(health, raw, mission=None)` is nonblocking. A background read can start every two seconds. A result is associated with the current DCS process, exporter session, aircraft type, exported unit label, and model time. Fresh advancing ownship telemetry, valid ownship coordinates, and an active cockpit are required. Paused, stale, disconnected, disabled, or changed sessions return no contacts. Network time counts toward the five-second contact expiry. Stopping or disabling the reader invalidates outstanding work.

The mission source uses `world.getPlayer()` as ownship authority. The player must exist, be active, and have positive finite life. Its ID, internal name, aircraft type, and coalition must remain unchanged across the read. Its aircraft type, nearby position (within five nautical miles), and model time must agree with the fresh exporter sample. The five-mile tolerance accommodates movement between the two sources; it does not establish a radar track.

Current exporter labels are not mission IDs or reliable IFF: live testing found exported `UnitName` **New callsign**, mission unit name **Aerial-3-1**, and mission callsign **Uzi11** for the same player. The exporter reported coalition label **Enemies** while the authoritative mission player coalition was numeric 2. No meaning is inferred from that label. `ownship_unit` preserves the exporter label for the frontend identity fence; `mission_player_unit_id` and `mission_player_unit_name` expose the distinct mission identity. DCS's native `getID()` returned a decimal string, which is validated and normalized. When the exporter does provide a numeric coalition, it must agree with the mission source.

Enemy means the opposite numeric red/blue coalition of the live player. Neutral units are excluded. Every individual live unit is considered in the airplane, helicopter, ground, ship, and native train group categories. Existing/active/positive-life checks exclude dead and not-yet-born units. Static objects, including aircraft placed as static objects, and scenery are outside this Unit feed. Country names are not used for allegiance.

Contact coordinates come from `coord.LOtoLL(unit:getPoint())`. Altitude is metres divided by 0.3048. Optional `speed_kt` is horizontal ground speed, calculated from world X/Z velocity using 3600/1852. No grid heading is labelled as true heading; heading is currently omitted.

At most 1,000 contact records are returned. The reader continues counting live eligible units and exposes `total_count`, `omitted_count` for unavailable coordinates, and `truncated` for the response limit. A mission exceeding 25,000 scanned units is unavailable rather than silently partial. Missing categories, disappearing handles, invalid IFF/identity, malformed coordinates, inconsistent counts, oversized responses, or an unavailable bridge cannot produce an apparently complete valid contact list.

The public object includes `status`, `mode: "mission-awareness"`, `source`, `age_s`, `session`, `aircraft`, `ownship_unit`, `single_player`, `model_advancing`, `contacts`, `total_count`, `omitted_count`, `truncated`, and `detail`. Available contacts contain `id`, `name`, `type`, `category`, `coalition: "red" | "blue"`, `lat`, `lon`, `altitude_ft`, optional `speed_kt`, and `age_s`. Available zero contacts is distinct from an unavailable source. The frontend additionally requires Automatic terrain and matching fresh ownship before drawing this layer.

Verification includes offline execution of the exact mission Lua against mocked DCS APIs, preflight/postflight transport tests, category/liveness/IFF cases, coordinate and identity validation, disable/close/session races, and age/model-time invalidation. The combined awareness and mission metadata suite passed 86 tests. An actual advancing single-player read returned Available in `tempMission`, F-22A, model time 2388.249–2388.307, ownship coalition 2, zero live opposing units, zero omitted units, and no truncation. This verifies the transport and valid empty result; nonzero category behavior is covered by the offline DCS API fixtures.
